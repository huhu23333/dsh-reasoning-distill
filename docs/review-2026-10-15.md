## 1. 缓存命中面（C 系列）

### C1【P0】【需决策】采用决定与「对请求可见」不在同一提交点 → 先发原文、后改蒸馏 ✓复核

- **证据（Lead 复核）**：`src/store.ts:243-278` 的顺序是 `structuredClone(await load)` → `mutate()`（**采用决定在此**）→ `mkdir/stat/chmod/stat/writeFile/rename`（**6 次真实 I/O**）→ `cache.set()`（**此刻条目才对 `peek`/`applyRewrites` 可见**）。源码注释自述 *"Mutators cannot expose their candidate through load/peek before the rename succeeds"*。
- **触发**：`timeoutMs` **有限**（`src/config.ts:190` 默认 0；`ruleBackstopMs()` 只要有一条规则为 0 就返回 0 → 无限等待，`src/engine.ts:1644-1651`）且等待上限恰好落在上述窗口内。`settle()` 到期放行（`src/engine.ts:1598-1627`）→ 该请求按旧账本派生 = **发原文**；rename 完成后条目可见 → 之后请求 **发蒸馏**。
- **为什么现有防护盖不住**：`abandonedNow()` 只在 `mutate()` **之前**的排队窗口生效（`src/engine.ts:2066-2085`）；超时后代码**特意保留**已提交条目，只把交接记 `skipped`（`src/engine.ts:2091-2099`），且 `handoff.state='skipped'` 并不禁用替换（`src/shared.ts:106-109`）。
- **影响**：违反插件自述的核心不变量「改写总在首次回放之前落地」，且无任何计价覆盖。
- **候选修法（择一，均需配套可失败的夹具）**：① 把「采用」与「可见」并入同一提交点（条目带 publish 门，`peek` 侧过滤未发布条目）；② 发布（rename 完成）后重验 deadline/generation，超时则回滚该 entry 为 `failed`，并保证回滚前不会有请求按新条目派生；③ 让等待上限只约束**蒸馏**、不约束**提交**（提交是本地文件写，短且有界），即到期后仍等提交落地再放行。
- 提出者：GPT-6 Sol（F2/1）、GPT-6 Astra（P1-1）、DeepSeek-V41-Flash（F2 近亲，并给出「所有规则都有限超时」这一前提）。

### C2【P1】【需决策】sidecar 不可读/读取超时 → 已发送的蒸馏版回退为原文，恢复后又变蒸馏 ✓复核

- **证据**：读失败只置 `storageBroken` 并阻止**新压缩**（`src/engine.ts:426-448`），而替换判据读 `store.peek`（`src/engine.ts:802-805`）→ peek 空 ⇒ 原文出站；每次 pre-step 重试读，读到后又变蒸馏。有限超时的放行是同一形态的另一条路（`src/engine.ts:283-303`）。
- **为何不直接修**：这是**有意的 fail-open**（坏 sidecar 绝不能卡住对话），修它要在「不卡对话」与「不改已发前缀」之间做产品取舍。
- 提出者：V41-Flash（F2/F3）、V4-Pro（#2）、Sol（#1/#3）、Astra（#3）——4/4 一致。

### C3【P1】【需决策】卸载/停用的行为**不确定**，且「文档声称已修」为假 ✓复核

- **证据**：包装只 `Object.defineProperty` 一次，**全文无任何还原代码**（`src/engine.ts:614,623`）；`deactivate()` 只置 `active=false`（`src/engine.ts:450-453`）；列表包装在 inactive 时**直接返回原方法结果、不跑还原**（`src/engine.ts:623-632`）。
- **关键**：宿主 `Session.deriveMessages()` 有增量派生缓存（仅 `contentGeneration` 变化时重建）；本插件的逐事件包装会把**替换后的消息**写进该缓存 ⇒ 停用后宿主**可能继续发蒸馏版**，直到缓存重建才回退；列表与逐事件两条读缝可能**暂时不一致**。
- **裁定**：V41-Flash 的「卸载**必然**回退原文」**过强**；Sol（F5）与 Astra（P2-1）正确。**这是 `47f7523`（两访问器改动）带来的新性质**。
- 附带：`README.md:230` 声称「`ctx.effect` 注册撤销器，卸载时恢复原方法（e2e 验证过）」**为假**；且 smoke 只把 effect 体收集进 `effects` 数组、**从未执行撤销**（`test/smoke.ts:99,145`）⇒ 卸载路径零测试。

### C4【P1】【需决策】分支账本继承失败（best-effort 吞错）→ 新分支缺账本：旧块回放原文 + 新旧 replay 元数据不一致

- **证据**：`carryLedgerToBranch` 捕获错误只告警、交接照常继续（`src/engine.ts:979-999`）；分支日志由 `message-edit` 的 splice 写入**新 reasoning 文本 + 原文 replay 载荷**（`scripts/patch-message-edit.py:425-435`），清洗完全依赖运行中的插件账本。
- **影响**：账本丢失/复制失败/插件停用后，会回放与新文本不对应的旧签名；DeepSeek 侧校验块数/类型但不校验签名与文本绑定，故会继续序列化该签名（服务端是否拒绝**未验证**）。
- **候选修法**：在**创建分支时就规范化** durable replay 元数据（改 `patch-message-edit.py` 的 splice，令其丢弃被替换块的 replay 载荷）——但这会改动已登记 sha256 的「已验证产物」，属**产品取舍**。
- 提出者：Sol（#3）、Astra（P1-2）——两条独立来源吻合。

### C5【P2】【设计取舍】共享同一 sidecar 的多个实例无跨进程串行化 → 最后写者覆盖 → 改写集跳变 ✓复核

- **证据**：写队列与缓存都属于单个 `SidecarStore` 实例（`src/store.ts:144-147,243-279`）；`update` 以本进程内存视图为基整文件重写（原子 rename，但无进程间锁）。
- 前提：两个宿主进程 / 热重载残留共享同一 `$DSH_HOME`。4/4 都提到。

### C6【P2】【不可修·宿主侧】token-meter 用**自由函数** `deriveEventMessage`，绕开插件的实例包装 → 估价仍按日志原文 ✓复核（Lead 上一轮已独立确认）

- **证据**：宿主 `packages/llm/token-meter/src/surface-fold.ts:111`、`surface-projection.ts:80` 调模块级函数；插件包装的是实例属性（`src/engine.ts:614`）。
- **影响**：存在「只剩包裹生效」的改写（交接失败/窗口期）时，宿主对上下文的估价**偏高** ⇒ 可能提前触发一次 compaction（多一次前缀重建）。方向保守（不会漏压）。修它需要替换 `ctx.tokenMeter` 或改宿主。

### C7【设计取舍·仅需文档】宿主 compaction 现在读派生（`47f7523` 起）→ 摘要用**蒸馏文本**生成；摘要一旦落日志，插件卸载后历史也永久含蒸馏文本

- 这是**改进**（压缩输入与请求一致），但需要在文档里说明「摘要承接的是蒸馏后的内容」。

## 3. 与 `dsh-ops` 共存（O 系列）

**静态层面：兼容（4/4 一致）**——无同名事件冲突（dsh-ops 只听 `session/event` 的 `sandbox/mode`、`agent/created|disposed`、`tools/*`，不碰 `agent/pre-step`/`agent/request`）、无 HTTP 路由、无客户端半边/UI 插槽、无设置命名空间争用、**不包装任何 Session 方法**、存储目录不重叠（`<home>/reasoning-distill` vs `<home>/dsh-ops`）、`inject` 互不依赖。

### O1【P1】【需决策】FastCtx 私有后台作业存活时的自动交接 = 实质不兼容

- **证据（两个独立来源吻合）**：dsh-ops 的 FastCtx 作业按 **Session 对象**记账，并拒绝非拥有者的 output/kill（`dsh-ops/lib/tools.js:693-717`），**不登记进宿主 jobs 表**；而本插件的 `skipWhileBusy` 只查宿主 jobs（`src/engine.ts:888-899`）⇒ 这类作业存活时仍会自动交接 → 新分叉会话**拿不到这些作业的控制权**。
- 必要前提：启用 dsh-ops 后台能力 + `danger-full-access` + 确有在跑作业 + 发生自动交接（权限门槛见 `dsh-ops/lib/tools.js:311-315`）。
- 对照：PTC `ops_batch` 路径**相反**（它登记 `owner=session.id` 到宿主 jobs，`dsh-ops/lib/ptc/index.js:117-140` ⇒ 能被 `busyWithWork` 看到并跳过）。

### O2【P2】【设计取舍·仅需文档】dsh-ops 改可见工具集 ⇒ system prompt/工具表变 ⇒ 另一个**独立**的前缀破坏源

- 属宿主对工具变化的正常处理（`packages/core/agent-loop/src/agent.ts:635-647`），不能归因于本插件；需在文档里说明「同一会话的工具/提示变化会造成缓存未命中，与本插件无关」。

### O3【P2】【可修】共同运行的技术前提未写明

- 本插件声明 `dshReleases 0.2.1-alpha.1`、Node `>=20`；dsh-ops 声明 Node `^22.19 || >=24` ⇒ 满足较低者不足以保证共存。应在 README 的共存说明里写明。
